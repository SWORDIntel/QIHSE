# Default parallel test suite

Run `make test` for the complete reviewed parallel schedule; `make test-serial` retains the original prerequisite order. `make test-parallel` is an explicit alias for the default schedule. The runner defaults to `TEST_JOBS=16` (bounded by CPU affinity); repository acceptance requires the complete `make test TEST_JOBS=32` run. The supported override range is 1–32. The runner builds the shared library, cluster daemon, admin CLI, standalone Redis server and gold-only binaries first; separate test processes then compile/run only approved independent targets concurrently. Unapproved or newly added `test-serial:` prerequisites run serially. The gold pack runs last, with the original gold runner validating the whole pack first and executing each approved offline workload in a private one-workload pack; other workloads remain serial. Changed pack versions, known-defect expectations or gaps fall back to the unpartitioned gold runner. The runners preserve failing exit codes and print a bounded failure log; no test is omitted for speed.

`python3 tests/run_parallel_suite.py --list` shows the plan without running it; `--parallel-only` runs just the approved lane for concurrency diagnosis and is **not** a full-suite result. New workloads require an explicit concurrency review before adding them to the allowlists in `tests/run_parallel_suite.py` or `tests/run_gold_parallel.py`: check shared test binaries, fixed ports, shared storage paths, background services and nested make targets. The test `make test-parallel-runner` checks manifest coverage and gold-output evidence. `TEST_JOBS` is bounded to 1–32; extra jobs affect only the approved parallel lane and offline gold workloads, not exclusive network/cluster tests. Running both full-suite entry points concurrently in the same checkout is unsupported because test recipes rebuild shared binaries.

On this checkout, the default sixteen-job schedule ran all 141 targets in 24m33s versus a prior sequential 36m22s; runtimes depend on machine load. The approved 56-target lane passed in 1m55s with eight jobs, 1m36s with sixteen and 1m28s with thirty-two. Doubling from sixteen to thirty-two saved only eight seconds in that lane while slowing individual tests, so sixteen remains the default. The full suite did **not** pass: the unimplemented DIRECTEYE aggregate queries failed. `test-consensus-mesh` passed this run but failed intermittently in earlier serial-lane runs; do not use the faster run as production readiness evidence.

Those measurements and failures are historical, not the current SQL compatibility status. The subsequent bounded source-readiness implementation passed all 23 application probes across psycopg2, psycopg v3 and asyncpg, and the complete 141-target suite passed with 32 jobs. Delivery adds staged public-header/link, C/C++, SDK verified-TLS, machine-token refresh and exact NUMERIC regressions; use the actual current runner manifest and final output rather than treating 141 as a fixed target count.

The application gate requires `pytest`, `psycopg2`, `psycopg` and `asyncpg` in the selected Python environment; `test-pgwire-app-compat` checks their imports before running. Install the clients in an isolated test environment and expose its interpreter on `PATH` when running the complete suite. Source-derived DIRECTEYE probes additionally require the real application source; an absent source or skipped probe is not readiness evidence. Fixtures create disposable authenticated TLS listeners and synthetic records only; no application DSN, production listener or actual DIRECTEYE database is changed.
